# SuperAgent 默认逐项交付与手动验收规范

> **文档定位**：SuperAgent 全局默认协作流程规范，可合并至 `AGENTS.md`，也可作为独立规则文件使用。  
> **适用架构**：Codex（规划与调度） + agy / Antigravity（开发实施） + 用户（最终手动验收）  
> **版本**：v1.0  
> **核心原则**：需求逐项追踪、开发结果透明、未完成项持续补齐、阻塞明确上报、用户最终验收。

---

## 1. 目标与适用范围

本规范应作为 SuperAgent 的**默认流程**，无需用户在每次开发任务中重复强调。除非用户明确要求采用其他工作模式，否则所有涉及功能开发、Bug 修复、界面改造、重构及需求变更的任务均按此流程执行。

主要目标：

1. 将原始需求转化为可追踪、可交付、可手动验收的逐项清单，降低需求遗漏风险。
2. 让 agy 对每个交付项报告真实开发状态、修改文件、检查结果和手动测试步骤。
3. 自动推进能够继续处理的未完成项，避免“只做了一部分就宣布完成”。
4. 对无法继续处理的问题明确阻塞原因、影响范围和所需协助，不做无意义重试。
5. 限定 Codex 的职责为规划、派发、协调和**交付清单的完整性检查**，避免不必要的全面代码审查和重复开发，从而控制 Token 消耗。
6. 始终由用户进行最后的**手动验收**；Agent 的任何自检结果都不能替代用户验收结论。

### 1.1 非目标

- **不要求 Codex 全面代码审查**：不逐文件审阅实现逻辑，不对所有代码做独立质量评估。
- **不将“验证”默认为自动化测试**：此流程中的“手动验收”是用户依据步骤亲自操作，确认需求是否满足；agy 可以按项目实际需要执行构建、Lint、局部测试等自检，但不能用其代替用户验收。
- **不要求 agy 逐项展示完整代码**：默认仅报告必要的修改摘要、文件及检查证据。
- **不允许以报告形式掩盖需求缺失**：文档齐全不等于功能完成。

## 2. 职责边界

| 角色 | 必须负责 | 不应负责 |
|---|---|---|
| **Codex** | 理解需求；拆分任务；编制编号清单；定义可观察的验收标准；分析依赖并派发 agy；汇总状态；核对交付字段/覆盖关系；重新派发未完成项；整理最终报告 | 全面代码审查；重复实现 agy 已派发的开发任务；把自己的判断当作用户验收；将未检查代码质量宣称为“已审查通过” |
| **agy（Antigravity）** | 实际编码、修改与自检；逐项回报状态；给出修改文件与真实检查结果；编写可复现的手动测试步骤；修复未完成和被驳回项；上报阻塞 | 擅自删除、合并或降低原始需求；把未执行的检查标为通过；将自己的交付状态写为“用户已验收” |
| **用户** | 按交付清单逐项手动测试；确认通过或驳回；对真正需要用户裁决的阻塞作出决定 | 不需要承担 Codex 与 agy 本应完成的需求追踪或开发自检工作 |

### 2.1 Codex 的“轻量级检查”范围

Codex 仅检查以下可由交付记录判定的事项：

- 原始需求是否全部建立唯一 ID；是否有遗漏或无故删除。
- 各项是否填写状态、实现摘要、修改文件、手动测试步骤和预期结果。
- agy 的状态是否自洽：有阻塞却写“完成”、部分实现却写“已就绪”等应退回说明。
- 未完成项是否已重新派发或明确阻塞；最终报告是否保留所有未解决事项。

**Codex 不因此推断源代码一定正确，也不负责全面代码审查。** 如发现需要阅读代码才能确认的问题，默认将其列为用户验收关注点或派回 agy 自检，而不是扩展 Codex 的职责。

## 3. 标准执行流程

```text
用户提出需求
    ↓
Codex 解析需求、拆分任务、分配需求 ID
    ↓
Codex 建立逐项交付清单与可观察的验收标准
    ↓
Codex 按依赖顺序向 agy 派发开发任务
    ↓
agy 开发 → 自检 → 逐项回报状态、变更文件、手动测试步骤
    ↓
Codex 进行轻量级交付完整性核对（不全面审查代码）
    ├─ 可继续完成的 TODO / PARTIAL / REJECTED → 重新派发 agy
    ├─ BLOCKED → 记录阻塞并确认下一步责任人/依赖
    └─ READY_FOR_ACCEPTANCE → 汇总进入用户待验收清单
    ↓
用户逐项手动验收
    ├─ 通过 → ACCEPTED
    └─ 不通过 → REJECTED → Codex 派发 agy 修复 → 再次手动验收
```

### 3.1 阶段 A：需求登记与规划（Codex）

1. 从用户原始需求中提取所有可独立验证的要求，包括功能、界面、交互、边界情况和明确约束。
2. 为每个要求建立稳定的需求 ID，格式推荐 `REQ-001`、`REQ-002`。跨轮修复不重编号。
3. 将较大的需求拆成可交付子项，但保留原始需求与子项的映射关系，防止拆分后漏项。
4. 为各项写明**验收标准**（实际表现是什么），避免仅使用“功能正常”“界面美观”等模糊说法。
5. 根据依赖关系与实施风险确定派发顺序；不能因实现成本高而擅自降级需求。

### 3.2 阶段 B：实现与自检（agy）

1. 依据派发范围实施开发，优先遵守现有项目架构与用户既定技术要求。
2. 每完成或推进一项，就同步更新清单状态。
3. 提供实际修改的文件路径、实现摘要、已执行的自检操作及真实结果；没有执行的内容写“未执行”。
4. 针对每一项提供用户可操作的**手动测试步骤**和对应**预期结果**，必要时注明测试数据、入口与前置条件。
5. 对尚未满足验收标准的项目，标记 `PARTIAL`、`TODO` 或 `BLOCKED`，不得直接标记交付就绪。

### 3.3 阶段 C：清单核对与补齐（Codex）

1. 比对原始需求 ID 和 agy 回传的交付 ID，查找缺失、重复、状态异常或交付字段缺失。
2. 只根据清单和交付摘要做**完整性检查**，不转化为全面代码审查。
3. 对可修复的未完成项进行增量派发，说明未满足的验收标准与本轮目标。
4. 对阻塞项登记原因、影响、已采取措施、下一步需要谁处理。
5. 当所有非阻塞项已达到 `READY_FOR_ACCEPTANCE`、阻塞项已如实说明后，生成可供用户手动验收的报告。

### 3.4 阶段 D：用户手动验收

1. 用户按照交付报告逐项操作，而非只阅读 agy 的完成声明。
2. 用户确认符合预期后，该项目才能进入 `ACCEPTED`。
3. 用户指出问题或结果不符，则改为 `REJECTED`，记录实际表现，由 Codex 重新派发 agy。
4. 未验收项目维持 `READY_FOR_ACCEPTANCE`；阻塞项目维持 `BLOCKED`，不得因汇报结束而自动关闭。

## 4. 统一状态定义与流转

| 状态 | 含义 | 允许谁设置 | 后续动作 |
|---|---|---|---|
| `TODO` | 需求已登记，尚未开始 | Codex / agy | 派发或开始开发 |
| `IN_PROGRESS` | 正在开发 | agy | 实现、自检、更新状态 |
| `PARTIAL` | 已做一部分，尚不满足完整验收标准 | agy | 继续补齐 |
| `READY_FOR_ACCEPTANCE` | agy 表示实现完成，并提供必要交付信息，等待用户验证 | agy 提交，Codex 汇总 | 用户手动验收 |
| `BLOCKED` | 当前无法继续，需要外部依赖、信息、权限或决策 | agy 报告，Codex 登记 | 解除阻塞后恢复实施 |
| `ACCEPTED` | 用户已明确验收通过 | **仅用户确认** | 关闭该需求项 |
| `REJECTED` | 用户验收未通过 | **仅用户反馈** | Codex 派发 agy 修复 |

**核心流转规则：**

- `TODO → IN_PROGRESS → READY_FOR_ACCEPTANCE → ACCEPTED`
- `IN_PROGRESS → PARTIAL → IN_PROGRESS`
- `TODO / IN_PROGRESS / PARTIAL → BLOCKED → IN_PROGRESS`（解除阻塞后）
- `READY_FOR_ACCEPTANCE → REJECTED → IN_PROGRESS → READY_FOR_ACCEPTANCE`

`READY_FOR_ACCEPTANCE` 只代表 agy **声称已完成开发并准备交付**，不代表用户确认功能正确。不能由 Codex 或 agy 自行写入 `ACCEPTED`。

## 5. 逐项交付清单的强制字段

每个需求项至少包含以下内容：

| 字段 | 要求 |
|---|---|
| 需求 ID | 唯一且稳定；与原始需求映射 |
| 需求描述 | 明确要实现什么 |
| 验收标准 | 用户实际能观察或操作验证的结果 |
| 当前状态 | 使用第 4 节的统一状态 |
| 实现说明 | 简述已完成行为，不夸大 |
| 修改文件 | 实际路径；无修改则说明 |
| agy 自检记录 | 做了什么、结果如何；未做写“未执行” |
| 手动测试步骤 | 入口、前置条件、操作顺序、测试数据（如适用） |
| 预期结果 | 与每个关键步骤对应的可观察结果 |
| 遗留问题/阻塞 | 若存在则说明影响及下一步 |

### 5.1 单项交付模板

```md
### REQ-001｜[需求名称]

- 原始需求：...
- 验收标准：...
- 开发状态：READY_FOR_ACCEPTANCE
- 实现说明：...
- 修改文件：
  - `src/...`
  - `src/...`
- agy 自检：
  - 已执行：`pnpm build` → 通过（如实际执行）
  - 未执行：...[如适用]
- 用户手动测试：
  1. 前置条件：...
  2. 进入页面/功能入口：...
  3. 执行操作：...
  4. 观察结果：...
- 预期结果：...
- 遗留问题：无 / [具体说明]
- 用户验收：待验收（仅用户可以确认通过）
```

**禁止填写虚构的文件路径、运行结果或已完成状态。** 上述命令仅为格式示例，不是所有项目的强制测试命令。

## 6. 未完成项补齐与阻塞处理

### 6.1 未完成项处理

- `TODO`：尚未实施，继续派发。
- `PARTIAL`：只派发缺失的行为或未达到的验收标准；保留已完成部分，避免无谓重做。
- `REJECTED`：以用户报告的实际问题和预期行为作为修复输入；修复后重新提供可执行的手动测试步骤。
- `READY_FOR_ACCEPTANCE` 但缺交付字段：先要求 agy 补交信息，不直接假定已验收。

### 6.2 阻塞认定

以下情况可作为阻塞：缺少必要权限、第三方环境不可用、接口契约不明、必须由用户做产品决策、外部依赖未交付、连续修复无进展等。

每个阻塞项必须包含：

1. **阻塞内容**：具体什么无法继续，而不是笼统写“有问题”。
2. **阻塞原因**：已确认原因与尚不确定之处应分开描述。
3. **影响范围**：哪些需求 ID 受影响，其他任务是否可以继续。
4. **已尝试措施**：简要列出实际采取的措施及结果。
5. **所需协助**：需要用户、第三方还是 agy 自身处理，提供清晰下一步。
6. **恢复条件**：满足什么条件即可重新进入 `IN_PROGRESS`。

### 6.3 防止无限循环

- 同一阻塞或同一失败点**连续两次补齐尝试没有实质进展**，停止机械重复派发，先汇报问题与解决选项。
- 可独立执行的其他需求继续推进，不因局部阻塞而停止整个项目。
- 未解决阻塞不得隐藏在最终报告中，也不得自动改写为已完成。
- 如果用户明确要求暂停、调整优先级或改变需求，以用户最新决定为准，并保留变更记录。

## 7. 增量交付与 Token 优化

### 7.1 首轮交付

第一次开发完成后，agy 返回完整的逐项交付清单，确保基线清楚、状态齐全。

### 7.2 后续修复轮次

后续只返回**发生变化的需求项**，至少包括：

- 本轮任务 ID 与修复目标；
- 状态变更：旧状态 → 新状态；
- 修改文件与改动摘要；
- 实际自检结果；
- 更新后的手动测试步骤和预期结果；
- 未解决问题或新的阻塞。

未变化项只需沿用已有记录，不重复输出完整需求、完整代码、全部历史日志或长篇分析。

### 7.3 Codex 最小化上下文

- 向 agy 派发**相关需求项 + 验收标准 + 必要上下文**，不反复粘贴全部项目历史。
- 将稳定的清单与状态持久化为项目文件，后续只传递增量。
- 不重复读取大量源码进行全面审查；仅在任务规划确实需要时查看必要项目结构和接口信息。
- 对同类未完成项批量派发；对有依赖关系的任务按顺序派发。
- 不将“交付摘要有无问题”扩大为“代码实现全面正确性审计”。

### 7.4 推荐项目记录文件

优先复用项目现有文档路径。没有既定方案时可采用：

- `docs/superagent/delivery-checklist.md`：需求 ID、验收标准、状态、责任与最终验收结论。
- `docs/superagent/delivery-log.md`：各轮 agy 增量交付与阻塞记录。

这只是推荐结构，不要求无条件创建多个文件。对小型需求，允许仅使用一份清单文件，避免过度工程化。

## 8. 最终交付报告模板

```md
# SuperAgent 交付与用户验收报告

## 本轮任务概览
- 任务名称：...
- 原始需求总数：N
- 待用户验收（READY_FOR_ACCEPTANCE）：N
- 用户已验收（ACCEPTED）：N
- 未完成（TODO / IN_PROGRESS / PARTIAL / REJECTED）：N
- 阻塞（BLOCKED）：N

## 逐项交付总览
| ID | 需求 | 开发状态 | 修改文件 | 用户验收 |
|---|---|---|---|---|
| REQ-001 | ... | READY_FOR_ACCEPTANCE | `src/...` | 待验收 |
| REQ-002 | ... | PARTIAL | `src/...` | 待验收 |
| REQ-003 | ... | BLOCKED | — | 待解决 |

## 手动验收步骤
### REQ-001
- 前置条件：...
- 操作步骤：1. ... 2. ... 3. ...
- 预期结果：...
- agy 已执行自检：... / 未执行

## 未完成与阻塞
### REQ-002
- 尚缺：...
- 下一步：继续派发 agy 补齐

### REQ-003
- 阻塞原因：...
- 已尝试：...
- 影响：...
- 所需协助：...
- 恢复条件：...

## 最终结论
- 开发交付状态：部分待验收 / 全部待验收 / 存在阻塞
- 用户最终验收状态：尚未完成
- 说明：仅用户确认后才能将对应需求标记为 ACCEPTED。
```

统计时各状态必须互斥，且各状态数量之和必须等于当前需求总数；不要将“待验收”统计成“已通过”。

## 9. 可直接并入 `AGENTS.md` 的默认规则

以下为精简版强制约束，可直接复制到 SuperAgent 全局 `AGENTS.md` 对应章节：

```md
## SuperAgent 默认交付与验收流程

1. 所有开发需求默认采用：Codex 规划/派发 → agy 开发/自检 → 逐项交付核对 → agy 补齐 → 用户手动验收。
2. Codex 必须依据原始需求生成稳定 ID 的逐项交付清单，并写明可观察的验收标准；不得遗漏、擅自删减或降低要求。
3. Codex 只负责任务规划、拆分、派发、进度协调和交付清单完整性核对；不进行全面代码审查、不代替 agy 编码、不代替用户验收。
4. agy 必须逐项报告：状态、实现说明、实际修改文件、自检记录、用户手动测试步骤、预期结果、遗留问题或阻塞。不得虚构执行结果。
5. 状态仅使用 TODO、IN_PROGRESS、PARTIAL、READY_FOR_ACCEPTANCE、BLOCKED、ACCEPTED、REJECTED；ACCEPTED 仅在用户明确确认后设置。
6. TODO、PARTIAL、REJECTED 等可处理项继续交给 agy 补齐；对缺少交付字段的已完成声明，要求 agy 补交。
7. BLOCKED 项必须说明原因、影响、已尝试措施、所需协助和恢复条件；相同问题连续两次无实质进展时，停止无效重试并上报。
8. 首轮返回完整清单，后续仅增量返回变更项与更新后的手动测试步骤；最终统一汇总报告，减少重复上下文和 Token 消耗。
9. agy 自检、构建或自动化测试结果均不代表用户验收；这里的“验收”特指用户根据步骤亲自操作确认。
10. 未经用户确认，不得宣布全部验收通过；存在未完成或阻塞时必须明确保留并呈报。
```

## 10. 执行优先级与例外

1. 用户最新明确指令 > 本文档默认流程；若有冲突，优先遵守用户当前要求。
2. 原始需求与验收标准是交付判断依据；任何范围变更均应记入清单。
3. 缺少关键信息时，先推进不依赖该信息的任务；受影响项保留阻塞状态。
4. 小需求可以简化文件数量和汇报篇幅，但不得省略逐项状态与用户手动测试步骤。
5. 安全、权限和数据保护等约束始终有效，不能以追求交付率为由绕过。

## 11. 最终强制原则

> **Codex 负责规划与任务派发，agy 负责实际开发与逐项交付，用户负责最终手动验收。**  
> **完整性核对不是全面代码审查；agy 自检不是用户验收；开发完成也不代表验收通过。**
