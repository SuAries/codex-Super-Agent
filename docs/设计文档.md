# SuperAgent 本地协作协议 v4.0（设计文档）

## 1. 核心分工与设计原则

SuperAgent 0.7.0（协议 4.0）全面实现《默认逐项交付与手动验收规范 v1.0》：

- **严格分工**：常规开发的代码编写与修复（含小修、样式文案、配置及启动/功能修复）由 Antigravity（agy）完成。GitHub/Gitee 发布、新版本及为该次发布进行的版本号、更新说明、打包、签名、公证、标签、产物上传、发布验证和修复仅由 Codex 模型执行。混合任务先拆分；发布例外见[最新补充规则](release-and-permissions.md)，优先于原规范的一般分工。用户最新明确要求优先。
- **常规开发中 Codex 负责规划、调度与交付完整性核对**：Codex 解析需求生成稳定 ID 清单、定义可观察验收标准（`acceptanceCriteria`）与依赖（`dependsOn`），并向 Worker 派发任务；对回传的交付清单仅执行**完整性核对**（字段齐全、ID 覆盖、状态自洽），不进行全面源码审查，不设强制性 Codex UI 操作卡点，不代替用户验收。
- **用户执行最终手动验收**：Codex 汇总并导出交付报告与手动测试步骤，由用户亲自操作验证。只有用户能通过 `acceptance` 命令确认 `ACCEPTED` 或反馈 `REJECTED`。Worker 自检或声称完成绝对不等于用户验收。
- **Worker 允许按需自检**：Worker 允许在必要时执行构建、Lint 或局部测试等自检（遵守用户明示约束，未执行如实标为 `NOT_RUN`）。默认不强制全仓自动化测试套件或 CI。

## 2. 状态机与流转模型 (协议 4.0)

### 需求项七项互斥状态

| 状态 | 含义 | 允许设置者 |
|---|---|---|
| `TODO` | 已规划，尚未开始 | Codex / Worker |
| `IN_PROGRESS` | 开发及自检中 | Worker |
| `PARTIAL` | 部分实现，尚不满足完整标准 | Worker |
| `READY_FOR_ACCEPTANCE` | 编码自检完成，字段齐全，等待用户验收 | Worker（Codex 汇总） |
| `BLOCKED` | 遇到外部依赖、权限或连续无进展阻塞 | Worker（Codex 登记） |
| `ACCEPTED` | 用户手动验证确认通过 | **仅用户（通过 `acceptance`）** |
| `REJECTED` | 用户手动验证未通过，指出具体缺陷 | **仅用户（通过 `acceptance`）** |

### 任务级状态流转

1. **`plan`**：登记 WorkOrder（包含 repo、goal、scope、constraints、acceptance、maxNoProgressRounds、maxConsecutiveFailures、defaultRunAutomatedTests 等，旧参数 `maxRepairRounds` 仅作兼容保留；默认新模式并非全任务两轮上限，而是针对同一失败项连续两次无进展熔断），生成任务 ID。默认 `reviewMode: "CODEX_DELIVERY_CHECK"`。
2. **`auto` / `run`**：首先根据显式 `taskKind` 及目标/需求的发布意图分流；发布任务返回 `CODEX_ONLY`，由当前 Codex 会话执行，不启动 agy 或其他模型。常规任务在独立工作树调用 Worker。Worker 在最终回复中输出单一 JSON 报文：
   - 首轮为 `reportKind: "FULL"`（`baseRevision: 0`），覆盖所有规划 ID；
   - 后续轮次为 `reportKind: "DELTA"`（`baseRevision: N`），仅包含变动项并标注 `oldStatus`；未变动项自动沿用。
3. **交付核对与自动推进**：
   - 若清单缺失、字段不齐或存在可继续完成的 `TODO` / `PARTIAL` / `REJECTED` 项，`auto` 自动向原 Worker 会话增量反馈并继续推进；
   - **局部阻塞不扩散**：单个项受阻标记为 `BLOCKED`，不影响其他无依赖关系的独立任务继续进行；
   - **连续无进展熔断（No-Progress 2）**：同一需求项或失败点连续 2 轮交付无实质进展（以状态、标准满足数或未完成清单变化为准），停止该项机械重试并标记为 `BLOCKED`，说明阻塞原因、影响、已尝试措施、所需协助与恢复条件；其他项继续推进。
4. **`AWAITING_USER_ACCEPTANCE`**：当所有非阻塞项达到 `READY_FOR_ACCEPTANCE` 时，任务转入用户待验收状态。Codex 导出交付与手动验收报告。
5. **用户手动验收与 `acceptance`**：用户按照测试步骤亲自操作后，通过 `acceptance --id <id> --file user-feedback.json` 录入决策。若全部项 `ACCEPTED`，任务转入 `ACCEPTED`；若存在 `REJECTED` 项，携带用户精准反馈重新派发原 Worker 会话修复。
6. **解除阻塞 `unblock`**：外部条件满足后，使用 `unblock --id <id> --requirement-id <req-id> --reason <text>` 重置为可处理状态。

## 3. 模块架构与职责

系统保持 6 个核心模块，配合纯辅助模块 `task-store/delivery-workflow.mjs` 处理交付工作流契约：

| 模块 | 职责 |
|---|---|
| Router | 规范 WorkOrder、scope、`acceptanceCriteria`、`dependsOn`、依赖环检测与参数规整。 |
| Scheduler | 管理任务状态流转（含 `AWAITING_USER_ACCEPTANCE`、`ACCEPTED`、`BLOCKED`、`CHANGES_REQUESTED`）。 |
| Worker Manager | 以参数数组调用 Worker，解析提取 FULL / DELTA 交付报文，维护 Worker 会话。 |
| Context Manager | 工作树隔离检查、改动范围安全守门、组装精准增量返工上下文。 |
| Watchdog | 监控子进程输出、超时、取消以及 POSIX 进程组退出状态。 |
| TaskStore | schema 5 任务持久化、任务锁管理、交付历史与用户验收历史记录。 |
| `task-store/delivery-workflow.mjs` | 纯辅助函数：处理 FULL/DELTA 校验、清单合并、七状态统计、连续无进展判定、用户反馈应用及报告渲染。 |

## 4. 历史兼容性

- 旧 schema 4 任务以及配置为 `CODEX_FUNCTIONAL_CHECK` / `CODEX_STARTUP_CHECK` 的任务保持兼容读取与流转。
- 旧版 `verify`（`STARTUP_ONLY` / `OPENED`）与 `confirm`（`PASSED`）历史保持原有语义，绝不自动升级为用户 `ACCEPTED`。
- 可选源码审查模块（`review-agent`, `review --file`, `inspect --code-review`）保持独立可选，默认交付流程绝不调用。

## 5. 安全与权限边界

- 严格遵循 Git 工作树隔离，基于已提交基线操作，保留未提交修改与无关代码；
- 严禁未经授权执行 `git commit`、`git push`、`git merge`、远程部署或分支清理；
- 严禁读取、存储或传输敏感凭据与 `.env` 文件；
- 命令行调用采用参数数组传递，严禁 `eval` 或拼接不可信命令；
- 常规任务默认 `agyPermissionPolicy: "AUTO_APPROVE"`，在受控隔离工作树的 CLI 会话中使用自动授权参数并保留终端隔离；以 `STANDARD` 可恢复通常审批。平台强制确认、管理员/显式拒绝、scope 与敏感数据保护继续有效，不修改全局 CLI、系统或 Codex 审批配置；详见[发布与权限规则](release-and-permissions.md)。
