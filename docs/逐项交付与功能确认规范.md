# Codex 逐项交付与功能确认规范（历史兼容 / 显式可选）

> [!NOTE]
> 在 SuperAgent 0.7.0（协议 4.0）中，全局默认流程已全面升级为[默认逐项交付与手动验收规范](default-delivery-workflow.zh-CN.md)（规范 v1.0）。
> 本规范对应原协议 v3.3 下的 `CODEX_FUNCTIONAL_CHECK` 模式，作为历史任务兼容及用户显式指定模式保留。在默认协议 4.0 下，Codex 仅负责规划派发与交付完整性核对，不设强制性 UI 交互卡点与全面源码审查门禁，由用户依据手动测试步骤进行最终手工业务验收。历史上的 `PASS` 结论绝不会被静默篡改为用户的 `ACCEPTED`。

## 1. 核心原则与分工（历史模式）

在显式配置 `reviewMode: "CODEX_FUNCTIONAL_CHECK"` 时：
- **所有代码编写与修复工作严格由 Antigravity 承担**：包括全部业务开发、一行小修、样式和文案调整、小配置修改、启动报错修复以及功能确认发现的问题修复。Codex 无直接编码例外，绝不替代编码。
- **Codex 仅负责三层功能确认**：
  1. **核对清单**：核对 Worker 提交的逐项交付清单是否精确覆盖 WorkOrder 中的所有需求 ID；
  2. **只读代码**：只读相关功能实现的必要差异代码（不遍历全仓、不做全面逻辑/安全/性能代码审查）；
  3. **简短操作确认**：真实启动 App 或在浏览器打开测试网页，针对各项需求进行逐项简短交互操作，核实实际功能表现与启动状态。
- **用户最终手工验收**：Codex 功能确认全部 PASS 且启动无报错后，系统进入 `READY_FOR_USER_TEST`，保持服务和窗口可用，交给用户最终手工验收。Worker 自报完成或 Codex 确认通过绝不代表用户已验收。
- **默认不执行全面源码审查与自动化测试**：不运行单元/集成/E2E脚本、Lint、typecheck 或 CI。使用电脑工具的界面操作属于本次授权的简短功能确认，不扩展为自动化测试套件。

## 2. Worker 结构化逐项交付清单规范

Worker 编码完成后，在最终回复中输出单一合法的 JSON 文本：

```json
{
  "summary": "简述本次任务实现的总体情况",
  "launch": {
    "command": "npm run dev",
    "target": "http://localhost:5173",
    "kind": "web"
  },
  "delivery": [
    {
      "requirementId": "REQ-1",
      "status": "IMPLEMENTED",
      "implementation": "在 src/components/Header.vue 中实现导航菜单与路由跳转",
      "entry": "点击顶部导航栏关于链接",
      "expectedResult": "页面平滑切换至关于视图，URL 变为 /about",
      "changedFiles": ["src/components/Header.vue", "src/router.js"]
    },
    {
      "requirementId": "REQ-2",
      "status": "BLOCKED",
      "implementation": "支付网关对接",
      "entry": "结算页点击微信支付",
      "expectedResult": "唤起微信支付二维码",
      "changedFiles": [],
      "reason": "缺少测试商户私钥与证书配置",
      "unblockConditions": "需配置环境变量 WECHAT_PAY_KEY_PATH"
    }
  ]
}
```

### 字段说明：
- `summary`: 总体修改说明。
- `launch`: 包含 `command`（启动或构建命令）、`target`（测试 URL、App 路径或命令）、`kind`（`web` / `app` / `cli`）。
- `delivery`: 逐项交付列表，必须与 WorkOrder 中的 `acceptance` 需求 ID 精确一一对应：
  - `requirementId`: 稳定的需求 ID（如 `REQ-1`, `REQ-2`），不得遗漏，不得包含未知 ID，不得重复。
  - `status`: 仅限 `IMPLEMENTED`（自报已实现）、`INCOMPLETE`（未完成）、`BLOCKED`（真实受阻）。
  - `implementation`: 具体的实现说明与关键代码位置。
  - `entry`: 功能验证入口或交互操作方式。
  - `expectedResult`: 预期的行为表现。
  - `changedFiles`: 本项涉及修改的相对文件路径数组。
  - `reason`: 当状态为 `INCOMPLETE` 或 `BLOCKED` 时必填，说明具体原因。
  - `unblockConditions`: 当状态为 `BLOCKED` 时必填，说明解除阻塞所需的外部前置条件。

> [!IMPORTANT]
> `IMPLEMENTED` 仅代表 Worker 编码自报完成，绝对不等于功能验证通过或用户已验收。

## 3. 自动补齐与阻断机制 (Auto Loop)

1. **自动补齐**：当 Worker 交付清单存在缺失、漏项、重复/未知 ID、格式畸形，或存在 `status: "INCOMPLETE"` 时，系统判定清单不完整。`auto` 命令在共享的返工预算（默认最多 2 轮）内，自动将具体缺失和未完成需求 ID 作为反馈，继续唤醒原 Worker 会话补齐。
2. **阻断停止**：当清单中存在 `status: "BLOCKED"` 项时，编排器立即停止任务并标记为 `BLOCKED`，明确列出受阻需求 ID、阻塞原因与待处理条件，不再空转消耗预算。
3. **预算耗尽**：若返工补齐轮次达到上限仍未全部 `IMPLEMENTED`，任务同样标记为 `BLOCKED`，由人工介入处理。
4. **全部实现进入确认**：只有当所有需求 ID 均为 `IMPLEMENTED` 时，任务才转入 `AWAITING_FUNCTIONAL_CHECK`，交由 Codex 会话执行逐项功能确认。

## 4. Codex 三层确认流程

当任务进入 `AWAITING_FUNCTIONAL_CHECK` 后，当前 Codex 会话执行以下操作：
1. **核对 Worker 清单**：使用 `inspect --id <id> --delivery` 查看交付详情，核对修改文件与入口。
2. **只读功能代码**：仅只读打开与需求相关的修改文件，确认关键逻辑存在且无明显破损，不扩散到全仓审查。
3. **真实操作确认**：
   - 根据 Worker 提供的启动说明启动目标服务或打开 App；
   - 实际打开浏览器或 App 窗口，确认启动阶段无可见报错；
   - 对每个需求进行简短交互（如点击按钮、输入表单、查看渲染），记录真实操作、预期与实际表现；
   - 纯 CLI/配置任务需核实真实命令输出或配置项事实，不可编造浏览器操作。

## 5. 功能确认 CLI 记录与报告规范

Codex 必须使用 `confirm` 命令独立持久化功能确认记录，与 Worker 自报及用户最终验收严格分离。

### CLI 命令示例：
```bash
node ~/.codex/super-agent/cli.mjs confirm --id <task-id> --file functional-check.json
```

### 完整报告 `functional-check.json` 格式：
```json
{
  "taskId": "c4d3a2b1-0000-4000-8000-000000000001",
  "workerAttempt": 1,
  "worktreePath": "/absolute/path/to/runtime/.workspaces/c4d3a2b1-0000-4000-8000-000000000001",
  "outcome": "PASSED",
  "verificationScope": "FUNCTIONAL_CHECK",
  "checkedBy": "CODEX_CURRENT_SESSION",
  "observedAt": "2026-11-11T08:00:00.000Z",
  "startup": {
    "kind": "web",
    "target": "http://localhost:5173",
    "opened": true,
    "errors": []
  },
  "items": [
    {
      "requirementId": "REQ-1",
      "result": "PASS",
      "codeEvidence": "src/components/Header.vue:20-45",
      "action": "在浏览器打开首页点击导航栏关于链接",
      "expected": "页面跳转至 /about 并渲染关于内容",
      "observed": "页面正常跳转并显示，未观察到报错"
    }
  ],
  "summary": "启动正常，已逐项完成简短功能操作确认"
}
```

### 确认结果流转规则：
- **PASSED**：所有需求均为 `PASS` 且启动无报错，任务转入 `READY_FOR_USER_TEST`，等待用户手工验收。
- **FUNCTIONAL_FAILED**：任何项为 `FAIL` 或启动报错，任务转入 `CHANGES_REQUESTED`，携带具体失败信息（需求 ID、代码依据、操作步骤与实际表现）反馈原 Worker 会话编码修复，共享返工额度。
- **NOT_VERIFIED / BLOCKED**：因环境、权限或外部依赖导致无法完成操作确认，如实标记为 `BLOCKED`，绝不假装通过。

## 6. 兼容性与边界说明

1. **旧任务兼容**：旧 schema 4 任务中 `reviewMode: "CODEX_STARTUP_CHECK"` 与 `CODEX_FUNCTIONAL_CHECK` 的任务继续有效，使用 `verify` 或 `confirm` 记录的历史保持原有语义，不会被伪造成新协议的用户 `ACCEPTED`。
2. **非源码审查**：功能确认仅针对相关功能的简短操作与必要代码核查，不生成代码快照覆盖矩阵，不调用独立的 review-agent。
3. **真实打开第一**：HTTP 200、进程存在或 Worker 自称成功都不能代替实际打开和简短操作。
